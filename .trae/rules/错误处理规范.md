# 错误处理规范

## 1. 错误码体系

### 1.1 错误码分类

错误码采用4位数字编码，分类如下：

| 错误码范围 | 分类 | 描述 |
|------------|------|------|
| 200-299 | 成功 | 操作成功 |
| 400-499 | 客户端错误 | 客户端请求错误或参数问题 |
| 500-599 | 服务器错误 | 服务器内部错误 |

### 1.2 通用错误码

| 错误码 | 描述 | 客户端处理建议 |
|-------|------|--------------|
| 200 | 成功 | 正常处理响应数据 |
| 400 | 参数错误 | 检查请求参数格式和内容是否符合要求 |
| 401 | 未授权 | 重新登录获取有效令牌 |
| 403 | 禁止访问 | 检查用户是否有足够权限执行此操作 |
| 404 | 资源不存在 | 确认请求的资源ID或路径是否正确 |
| 405 | 方法不允许 | 检查请求方法是否正确（GET/POST/PUT/DELETE等） |
| 406 | 不接受的内容类型 | 检查Accept请求头是否符合服务器要求 |
| 415 | 不支持的媒体类型 | 检查Content-Type请求头是否正确 |
| 429 | 请求过于频繁 | 降低请求频率，考虑添加重试机制 |
| 500 | 服务器内部错误 | 联系系统管理员，记录错误日志 |
| 501 | 接口未实现 | 检查API版本是否正确 |
| 502 | 网关错误 | 检查网络连接，联系系统管理员 |
| 503 | 服务不可用 | 稍后重试，或联系系统管理员 |
| 504 | 网关超时 | 检查网络连接，或增加超时时间 |

## 2. 错误响应格式

### 2.1 通用错误响应格式

所有API错误响应采用统一格式：

```json
{
  "success": false,
  "message": "错误描述信息",
  "data": null,
  "code": 错误码
}
```

### 2.2 参数错误响应格式

当参数验证失败时，响应应包含具体的参数错误信息：

```json
{
  "success": false,
  "message": "参数验证失败",
  "data": {
    "errors": [
      {
        "field": "参数名",
        "message": "参数错误描述"
      }
    ]
  },
  "code": 400
}
```

### 2.3 批量操作错误响应格式

批量操作失败时，响应应包含成功和失败的详细信息：

```json
{
  "success": false,
  "message": "批量操作部分失败",
  "data": {
    "successCount": 成功数量,
    "failCount": 失败数量,
    "failDetails": [
      {
        "id": 操作对象ID,
        "message": "失败原因"
      }
    ]
  },
  "code": 错误码
}
```

## 3. 后端错误处理流程

### 3.1 异常处理层次

1. **控制器层**：处理请求参数验证异常和业务异常
2. **全局异常处理器**：统一处理所有未捕获的异常
3. **过滤器层**：处理认证和授权异常
4. **中间件层**：处理跨域、请求限流等异常

### 3.2 异常处理实现

#### 3.2.1 自定义异常类

```java
// 基础业务异常类
public class BusinessException extends RuntimeException {
    private int code;
    private Object data;
    
    // 构造方法
    public BusinessException(int code, String message) {
        super(message);
        this.code = code;
    }
    
    public BusinessException(int code, String message, Object data) {
        super(message);
        this.code = code;
        this.data = data;
    }
    
    // getter方法
    // ...
}
```

#### 3.2.2 全局异常处理器

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    
    // 参数验证异常处理
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResponse handleValidationException(MethodArgumentNotValidException e) {
        List<Map<String, String>> errors = e.getBindingResult().getFieldErrors().stream()
            .map(error -> {
                Map<String, String> errorMap = new HashMap<>();
                errorMap.put("field", error.getField());
                errorMap.put("message", error.getDefaultMessage());
                return errorMap;
            })
            .collect(Collectors.toList());
        
        return ApiResponse.error(400, "参数验证失败", Map.of("errors", errors));
    }
    
    // 业务异常处理
    @ExceptionHandler(BusinessException.class)
    public ApiResponse handleBusinessException(BusinessException e) {
        return ApiResponse.error(e.getCode(), e.getMessage(), e.getData());
    }
    
    // 资源不存在异常处理
    @ExceptionHandler(NotFoundException.class)
    public ApiResponse handleNotFoundException(NotFoundException e) {
        return ApiResponse.error(404, e.getMessage());
    }
    
    // 权限不足异常处理
    @ExceptionHandler(AccessDeniedException.class)
    public ApiResponse handleAccessDeniedException(AccessDeniedException e) {
        return ApiResponse.error(403, "禁止访问");
    }
    
    // 未授权异常处理
    @ExceptionHandler(AuthenticationException.class)
    public ApiResponse handleAuthenticationException(AuthenticationException e) {
        return ApiResponse.error(401, "未授权");
    }
    
    // 通用异常处理
    @ExceptionHandler(Exception.class)
    public ApiResponse handleException(Exception e) {
        // 记录详细错误日志
        log.error("系统异常:", e);
        return ApiResponse.error(500, "服务器内部错误");
    }
}
```

### 3.3 错误日志记录

1. **详细错误日志**：记录异常堆栈信息、请求参数、用户信息等
2. **错误级别**：根据异常类型设置不同日志级别（ERROR/WARN/INFO）
3. **日志格式**：统一日志格式，便于日志分析和监控
4. **敏感信息**：避免在日志中记录敏感信息（如密码、令牌等）

## 4. 前端错误处理流程

### 4.1 请求拦截器

```javascript
// 请求拦截器
request.interceptors.request.use(
  config => {
    // 添加认证令牌
    const token = localStorage.getItem('token');
    if (token) {
      config.headers.Authorization = `Bearer ${token}`;
    }
    return config;
  },
  error => {
    return Promise.reject(error);
  }
);
```

### 4.2 响应拦截器

```javascript
// 响应拦截器
request.interceptors.response.use(
  response => {
    const res = response.data;
    
    // 正常响应
    if (res.success) {
      return res;
    } else {
      // 业务错误
      return Promise.reject(new Error(res.message || 'Error'));
    }
  },
  error => {
    if (error.response) {
      const { status, data } = error.response;
      
      // 根据状态码处理不同错误
      switch (status) {
        case 401:
          // 未授权，跳转到登录页
          localStorage.removeItem('token');
          router.push('/login');
          break;
        case 403:
          // 禁止访问，显示提示
          ElMessage.error('没有权限执行此操作');
          break;
        case 404:
          // 资源不存在
          ElMessage.error('请求的资源不存在');
          break;
        case 429:
          // 请求过于频繁
          ElMessage.error('请求过于频繁，请稍后重试');
          break;
        case 500:
          // 服务器错误
          ElMessage.error('服务器内部错误，请联系管理员');
          break;
        default:
          // 其他错误
          ElMessage.error(data.message || '请求失败');
      }
    } else if (error.request) {
      // 请求已发送但没有收到响应
      ElMessage.error('网络异常，请检查网络连接');
    } else {
      // 请求配置错误
      ElMessage.error('请求配置错误');
    }
    
    return Promise.reject(error);
  }
);
```

### 4.3 页面错误处理

#### 4.3.1 错误边界组件

```vue
<template>
  <div class="error-boundary">
    <slot v-if="!hasError">
      <!-- 正常内容 -->
    </slot>
    <div v-else class="error-content">
      <el-icon class="error-icon"><WarningFilled /></el-icon>
      <h3>页面发生错误</h3>
      <p>{{ errorMessage }}</p>
      <el-button type="primary" @click="handleRetry">重试</el-button>
    </div>
  </div>
</template>

<script setup>
import { ref, onErrorCaptured } from 'vue';
import { WarningFilled } from '@element-plus/icons-vue';

const hasError = ref(false);
const errorMessage = ref('');

onErrorCaptured((err) => {
  hasError.value = true;
  errorMessage.value = err.message || '未知错误';
  console.error('页面错误:', err);
  return false;
});

const handleRetry = () => {
  // 刷新当前页面
  location.reload();
};
</script>
```

// API调用示例

## 5. 错误处理最佳实践

### 5.1 后端开发最佳实践

1. **明确的错误码**：为每个业务错误定义唯一的错误码
2. **详细的错误信息**：提供清晰、准确的错误描述
3. **统一的异常处理**：使用全局异常处理器统一处理所有异常
4. **适当的错误日志**：记录足够详细的错误信息，便于排查问题
5. **事务管理**：确保在发生错误时，事务能够正确回滚
6. **参数验证**：在控制器层进行严格的参数验证
7. **友好的错误提示**：避免向客户端暴露内部错误细节

### 5.2 前端开发最佳实践

1. **统一的错误处理**：使用响应拦截器统一处理API错误
2. **用户友好的提示**：根据错误类型显示适当的错误提示
3. **重试机制**：对网络请求失败提供重试选项
4. **错误边界**：使用错误边界组件捕获页面渲染错误
5. **状态管理**：在状态管理中记录错误状态，便于组件访问
6. **日志记录**：在开发环境记录详细错误日志，便于调试
7. **降级处理**：当API不可用时，提供适当的降级方案

### 5.3 前后端协作最佳实践

1. **统一错误码**：前后端使用相同的错误码体系
2. **文档同步**：及时更新错误码文档，确保前后端一致
3. **错误信息一致**：同一错误的错误信息在前后端保持一致
4. **定期审查**：定期审查错误处理逻辑，优化错误处理流程
5. **异常测试**：为各种错误场景编写测试用例

## 7. 错误码管理

### 7.1 错误码维护

1. **集中管理**：所有错误码集中在一处定义和维护
2. **版本控制**：对错误码进行版本控制，避免冲突
3. **文档更新**：及时更新错误码文档，确保与代码一致
4. **定期清理**：定期清理不再使用的错误码

### 7.2 错误码扩展

1. **预留范围**：为每个模块预留足够的错误码范围
2. **扩展规则**：扩展错误码时遵循现有分类规则
3. **向后兼容**：避免修改或删除已有的错误码

## 8. 总结

错误处理是系统稳定性和用户体验的重要组成部分。本规范定义了统一的错误码体系、错误响应格式、前后端错误处理流程和最佳实践，旨在确保系统在发生错误时能够提供清晰、一致的错误信息，便于问题排查和用户理解。

前后端开发人员应严格遵循本规范进行错误处理实现，定期审查和优化错误处理逻辑，提高系统的稳定性和用户体验。
